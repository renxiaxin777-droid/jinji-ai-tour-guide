## 1. 需求分析

### 1.1 背景与痛点

山西是「中国古建筑博物馆」：现存古建筑约 **2.8 万处**（2024 年山西省政府新闻发布会口径）；其中**元代及以前木构建筑 509 处**，为全国同类建筑最集中的省份。但来山西的游客普遍面临三难：

1. **看不懂**——唐构、辽塔、金殿、悬塑，术语劝退，普通游客走马观花；
2. **找不全**——精华古建散布各县乡，信息零散，攻略靠口口相传；
3. **不敢信 AI**——普通大模型聊天机器人「直接作答」，年代数据张口就来，答错无从察觉（见 §6 对照实验）。

### 1.2 用户画像与典型场景

| 用户 | 特征 | 他会问什么 | 晋迹怎么答 |
|---|---|---|---|
| ① 黑神话玩家打卡党 | 追游戏取景地、拍照发圈 | 「黑神话在山西的取景地有哪些？」「应县木塔在哪拍剪影最好？」 | 一次检索返回 9 处取景地，附年代与机位贴士 |
| ② 古建爱好者 | 懂一些、要深度 | 「南禅寺和佛光寺谁更早？」「山西还有哪些唐代木构？」 | 先查再答，年代精确到年号，附梁思成考察故事 |
| ③ 亲子家庭 | 要故事、要轻松 | 「给孩子讲讲晋祠有什么好玩的？」 | 检索+讲解，重点亮点、贴士，可一键语音播放 |

> 说明：三类画像来自需求调研推演，尚未做用户访谈验证（见 §14 待验证事项），当前表述为「预期价值」。

### 1.3 应用案例走查（以「黑神话玩家」为例，实测实录）

- 用户：「黑神话悟空在山西的取景地有哪些？」
- 晋迹工作流（实测工具调用序列）：
  1. `search_attractions(query="黑神话取景地")` → 一次检索命中 9 处取景地条目（工具返回上限 10）；
  2. 基于返回资料组织回答：列出云冈石窟、悬空寺、应县木塔、佛光寺、双林寺、崇福寺、隰县小西天、玉皇庙、铁佛寺，附年代与看点；
  3. 用户点「🔊 语音讲解」→ edge-tts 合成语音播报。
- 截图见 `docs/assets/shot3_conversation.png` 与 `docs/assets/jinji-workflow.png`。

## 2. 设计思路

### 2.1 核心原则：先查再答（程序级约束，不只是提示词）

晋迹不是「套壳聊天」：回答古建事实前必须先取得知识库资料。这道约束有**两层保障**：

1. **提示词层**：系统守则要求「知识库没有的信息要明确说明，不得编造年代、数据」；
2. **程序层**：`run_agent()` 在作答前检查——若该问题在知识库中有命中、而模型一次工具都没调用就想直接作答，程序会**拦截并强制补一轮检索**（`agent.py` 的 `_need_source` / `_enforced` 逻辑），不依赖模型自觉；同时把「是否检索、命中什么」记录在工具调用步列表中。

实测（离线单测）：以脚本模拟「模型无视工具直接作答」的响应，程序确实拦截并触发补检索；对知识库无命中的闲聊问题则不误触发。

> 表述口径：晋迹提供的是**通过检索与来源展示提高回答可核查性**，不等于「每句话都绝对正确」。

### 2.2 Agent 工作流架构

```
用户提问 → 大模型判断（deepseek-chat）→ 调用工具（检索/详情/规划）
        → 本地知识库返回真实资料 → 基于资料组织讲解 → 语音播报
```

架构图见 `docs/assets/agent-arch.png`。工具调用全程在 UI 的「🧠 智能体工作流 · N 次工具调用」面板可视化展示，每次调用的工具名、参数与返回数据都可查看。

### 2.3 与普通大模型直答的差异

| | 普通 AI 直答 | 晋迹（工具调用智能体） |
|---|---|---|
| 资料来源 | 模型记忆，无外部约束 | 先查本地知识库，基于资料作答 |
| 编造风险 | 存在（见 §6 实测案例） | 提示词 + 程序双层约束，未收录明确说不知道 |
| 可解释性 | 无 | 每次调用可见（工作流面板） |
| 可更新性 | 需改模型或提示词 | 知识库纯数据更新，零改代码 |

> 关于 RAG：检索增强（RAG）是一种方法，智能体可以使用它。晋迹的差异点在于把检索、详情、规划三类工具串成闭环并把执行过程可视化，而不是宣称与 RAG 互斥。

## 3. 功能模块

| 模块 | 功能 | 实现 |
|---|---|---|
| 知识库检索 | 按景点名/城市/区域/主题检索 | `search_attractions` 工具 + 关键词/词元双通道检索（kb.py） |
| 景点详情 | 单景点年代、看点、贴士、来源 | `get_attraction_detail` 工具 |
| 行程规划 | 按天数/城市/兴趣编排路线 | `plan_itinerary` 工具：5 条精选路线 + 任意组合动态编排；**尊重天数约束**（每日 2–3 处，超出部分列为「备选」而非硬塞），**覆盖范围外明确提示**（问北京会说明仅覆盖山西），输出定位为「行程草案」，不含实时车程与开放信息 |
| 语音讲解 | 回答一键合成语音 | edge-tts 在线女声（缓存复用）；网络失败时回退本地 pyttsx3/SAPI 女声 |
| **导览模式（四档）** | 小白导览 / 进阶讲解 / 硬核断代 / 🧭 行程规划师 | 四套系统提示词（`LEVEL_PROMPTS`）：basic 通俗讲故事、pro 术语+人话解释、hardcore 断代依据+学界争议、planner 逐构件读古建+肉眼观察方法+实操贴士；其中 hardcore 与 planner 档供给「建筑形制 / 断代依据 / 冷知识争议」字段（HARDCORE 知识层 16 处重点古建） |
| **拍照识古建**（实验功能） | 上传照片 → 视觉识别形制 → 检索知识库 → 讲解 | 图文共用 `deepseek-chat` 配置；**经实测可用**（正例：应县木塔照片识别出八角五层、平座栏杆、收分；反例：网页截图与架构图会被判为「非古建」）。DeepSeek 官方视觉文档示例模型为 `deepseek-flash`，故保留「实验」定位，演示前需现场复测 |
| **断代主题路线** | 按朝代演变编排：唐→五代→宋→辽→金→元，每节点附形制特征 | 断代路线预设（完整为 2 日）；用户要求更短天数时截取前段并说明。定位为「文化学习路线」，实际出行顺序需另行安排 |

附：离线演示模式（§7）、数据来源字段（§5）。

**差异化定位**：普通导览告诉你它「是什么」，晋迹告诉你它「为什么是它」——硬核档能讲清「佛光寺东大殿为什么判定为唐构」（七铺作双杪双下昂、梁下墨书题记 857 年、梁思成 1937 年考据）；断代路线带你读「中国木构建筑的一千年」；拍照识别让游客不需要懂术语，拍一张就有据可依的讲解。

## 5. 数据来源说明

- 知识库 **35 处古建条目**，每条均带 `source` 字段，分「全国重点文物保护单位名录」「世界文化遗产名录」「景区公开资料」三类；
- **来源与结论分开对待**：`source` 用于支撑「保护身份」（是否国保、是否世界遗产）；**年代、形制、学界争议等具体结论另需出处**。当前演示涉及的 5–8 处重点古建已逐条复核，记录维度为「结论 — 来源标题 — 发布机构 — 核验日期」；
- **已修正案例**：晋祠条目原有「圣母殿重建于北宋天圣年间（984 年）」混用年号与年份（天圣为 1023–1032 年），已改为「北宋天圣年间（1023—1032 年），现存为北宋原构」；
- 讲解时系统守则要求重要结论注明来源（如「据全国重点文物保护单位名录」）；
- 数据治理：内容由公开资料整理并经人工校对；**存疑条目在提交前下架或标注**，未经核实的硬核结论不进入演示；
- 扩展性：新增景点为纯数据操作（在 `kb.py` 增加一个字典条目），无需改动任何代码逻辑。

## 6. 智能体 vs 套壳 对照实验（真实证据）

**实验设计**：同一问题分别输入「普通大模型直答」（无知识库、无工具，DeepSeek 官方 API 裸调用）与「晋迹」（工具调用+知识库），记录真实输出。

**问题**：「介休后土庙建于哪一年？」

**普通大模型直答**（实测输出，截图 `docs/assets/plain-llm-direct.png`）：

> 「介休后土庙的始建年代没有确切记载，通常认为创建于**南朝宋孝武帝大明元年（457年）**，也有一说为北魏时期。现存建筑多为明洪武至正德年间重修或扩建……」

⚠️ 问题：介休地处今山西，457 年属北朝（北魏）辖区，「南朝宋」年号不适用于该地；且始建年代公开资料无确考，该说法无公开出处支持——典型幻觉（编得具体、有模有样、无法察觉）。

**晋迹回答**（实测输出，截图 `docs/assets/jinji-workflow.png`）：

> 「关于介休后土庙的始建年代，我的知识库里暂时没有收录它的独立条目，因此无法给出确切的创建年份——涉及年代数据，我不能凭印象编造。可确定的相关信息：后土庙确为介休城内值得一看的古建……建议以庙内碑刻或《介休县志》为准。」

同时工作流面板展示了 3 次真实工具调用（`get_attraction_detail` → 未命中 → 两次 `search_attractions` 放宽检索）。

**结论**：同一问题，直答模型给出貌似精确的错误年代；晋迹「查不到就明确说查不到」。这正是工具调用型智能体「有据可依」的核心价值。

**证据强度说明（不夸大）**：
- 本实验为**单个案例**，能说明「个别问题上直答会编」，**不能**据此得出「晋迹整体更准确」或「普通 AI 一问就编」；
- 另测两题（「铁佛寺彩塑作者」「应县净土寺朝代」）中，普通模型也答得较为克制，因此只选用真实发生的幻觉案例作为证据；
- 系统化的三条件对照（同模型直答／同模型+严谨提示词／晋迹）列为**待完成测试**，见 §14。

## 7. 离线演示与网络依赖说明

- **离线演示模式**：未配置 API Key、或启动时设置 `MOCK_LLM=1`，应用进入 MOCK 模式——本地固定脚本完整走完「判断→工具调用→知识库返回→回答」全流程，界面与真实模式一致。它用于**流程演示与开发自测**，不等于离线运行真实大模型（MOCK 的最终回复是预置文本）；
- **已配置 Key 后断网**：不会自动切换，工具调用会直接报网络错误——**决赛现场须联网，或以录屏视频兜底**；
- **语音**：edge-tts 为在线服务（需联网）；项目另备 pyttsx3/SAPI 本地女声兜底路径（`requirements.txt` 已列入 pyttsx3），首次使用前建议在干净环境复测一次；
- 意义：把「网络不可控」的风险显式管理起来，而不是假设系统会自动兜住。

## 8. 运行与部署说明

- **本地一键启动**：双击 `启动晋迹.bat`（自动建虚拟环境、装依赖（国内镜像，失败自动切 uv）、启动并打开浏览器）；

## 12. 常见问题（评委预判 Q&A）

1. **为什么叫智能体？** 模型先判断需要什么资料、再调用工具、读取返回结果继续推理，最后基于资料作答，执行过程在界面可视化。同时如实说明：工具选择与流程由提示词与规则编排，属**轻量工具调用型智能体**。
2. **与普通大模型 / RAG 的区别？** 用同一模型的对照结果说明差异（§6）。检索增强（RAG）是一种方法；晋迹把检索、详情、规划串成闭环并把执行过程可视化，二者可组合，不互斥。
3. **查过资料就一定正确吗？** 分三层看：来源可靠性（`source` 字段）、检索相关性（命中的条目是否对题）、回答是否忠于资料（提示词 + 程序约束）。三者都有检查机制，但**不等于绝对正确**。
4. **数据可靠性？** 逐条带 `source`；年代、形制等具体结论另需出处（§5）；查不到就明说。
5. **知识库只有 35 处，价值在哪？** 这是**试点范围**：选取山西最核心的一批古建与 5 条经典线路验证产品形态。价值在于「规模小但可核查 + 扩展成本极低」——新增景点是纯数据操作、零改代码。
6. **行程真能走完吗？** 当前提供的是**行程草案**：已约束天数与每日景点数、覆盖范围外会提示；但**不含实时车程与开放信息**，正式出行可行性需再核对。
7. **断网还能做什么？** 分三层说明：本地检索可用、MOCK 流程演示可用、真实模型问答与在线语音不可用（详见 §7）。
8. **AI 写了大量代码，团队做了什么？** 见 §14.2 的三项可展示成果，关键实现可由成员现场解释。
9. **商业化路径？** 景区定制导览、博物馆讲解辅助、文旅小程序嵌入口。

| 三条件对照测试 | 仅 1 个案例（§6） | 20 题（库内事实／未收录／歧义／路线约束），比较「同模型直答」「同模型+严谨提示词」「晋迹」 |
| 拍照识别稳定性 | 实测正例 1 次 + 反例 2 次 | 补四类样本（已收录古建／未收录古建／普通建筑／非建筑）复测 |
| 行程可行性 | 无交通与开放信息 | 与景区公开开放信息核对后，再称「可执行攻略」 |
| 用户反馈 | 尚未收集 | 现场演示时收集试用反馈 |

### 14.2 团队贡献（三项可展示成果）

1. **古建事实与来源的组织方式**：35 条目 schema（name/aliases/city/era/tags/summary/highlights/tips/wukong/source）+ 16 条硬核断代知识层，把「讲得懂」与「查得到」拆成两个维度；
2. **检索失败后的处理规则**：命中不足时的补充检索、明确回答「未收录」、覆盖范围外提示、程序级「先查再答」拦截（§2.1）；
3. **面向不同游客的讲解与路线约束**：四种导览模式 + 行程天数/区域约束与备选机制。

> 定位说明：晋迹是**轻量工具调用型智能体**（规则编排 + 大模型判断），不是全自动自主智能体。国产大模型对应大赛鼓励方向，我们不将其表述为「确定加分」。
